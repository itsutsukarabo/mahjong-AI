## 議題1: wait_f1 の位置づけ

- **wait_f1 はサブ指標**。early stop / model.pt 保存の基準は `val_eae`
- wait_loss は `LAMBDA_WAIT=0.5` でトータル loss に入っているが評価基準ではない
- v32 との wait_f1 差は「v37 が wait を悪く学習した」ではなく「val_eae 優先の結果 wait が若干犠牲になった」可能性が高い

---

## 議題2: wait_loss の重み付け（λスケーリング）

**ユーザー提案:** 副露 n 回したプレイヤーには `LAMBDA_WAIT * (n+1)` を適用する

**背景:**
- wait_f1 を当てやすいケース: 副露ありプレイヤー
- 当てにくいケース: 風露なし（メンチン）プレイヤー
- 副露ありプレイヤーは副露牌自体が公開情報になるため待ちが絞りやすい

**重要な補足（ユーザー指摘）:**
- 副露ありプレイヤーの待ちを絞る**最も重要な情報**は「何を鳴かなかったか」= pass_pon_signal / pass_chi_signal
- 副露する前後に積み上がるパス情報が、残り手牌の範囲を決定的に絞る
- 副露数 n とパス情報量はある程度相関するため、`n+1` 倍は合理的な近似

**非線形 vs 線形:**
- パス情報が積み上がる形態 → 情報量の増加は副露数に対してほぼ**線形**
- 非線形にする強い理由はない

**結論:** `LAMBDA_WAIT * (n+1)` の線形スケーリングで試す価値あり

## 議題3: パス情報の学習への活用（最重要課題）

### 問題の核心

現在の `pass_pon_signal` / `pass_chi_signal` は **集計値（34次元バイナリベクトル）** であり、以下の情報が失われている:

- パスのタイミング（順序）
- 複数パスの組み合わせから導ける推論チェーン
- 「パスした後に同じ牌を自ら切った」等の複合事象

**ユーザーが期待する推論例:**
1. 向かいが 7m を切って**ポンしていない** → 7m の対子なし → さらに 7m を手から切った → **8m9m が通ると推測できる**
2. チーできる左プレイヤーが切った牌 → **待ちになるケースがほとんどない**

これらは現状の集計ベクトルでは学習困難。

### 根本解決策: パスイベントもトークン列に追加（v38 候補）

```
DISCARD_TOKEN:   tile, turn, is_tsumogiri, is_riichi_decl, is_red, player_role  ← 現行
PASS_PON_TOKEN:  tile, turn, player_role                                         ← NEW
PASS_CHI_TOKEN:  tile, turn, player_role                                         ← NEW
```

Transformer がイベント系列として `PASS_PON(7m) → DISCARD(7m)` という因果チェーンを学習できる。

**課題:** states_v22.ndjson にパスイベントは未記録 → 計算で追加は可能だがデータ量が膨大になる懸念

### 代替案: 制約ロスでモデルを誘導（アプローチB）

```python
# pass_pon[t]=1 なのに対子ブロックの確率が高い → ペナルティ
pass_pon = feat[:, :, HI_PON_PASS:HI_PON_PASS+34]  # (B, P, 34)
loss_constraint = (pass_pon * prob_pair_blocks).mean() * LAMBDA_CONSTRAINT
```

- ラベル修正（アプローチA）は**不可**：ラベルはすでに正しい（スルーした人の対子は元々ない）のでラベルを削っても意味がない
- アプローチBは「モデルが矛盾した予測をしたら罰則」という形で推論を誘導できる
