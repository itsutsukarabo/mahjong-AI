# 手牌推測モデル v6悪化 原因調査実験計画

最終更新: 2026-06-06

---

## 背景

v5 (219次元, Transformer) → v6 (371次元, 同アーキテクチャ) で精度が低下した。

| モデル | 入力次元 | test_acc | test_loss |
|--------|---------|----------|-----------|
| v5     | 219     | 0.8025   | 0.4679    |
| v6     | 371     | 0.7891   | 0.4938    |

v6 では以下を一括追加した:
- 他家2人の捨て牌 (+88次元)
- 赤牌捨てシグナル (+3次元)
- ポンスルー信号 (+34次元)
- 場風・自風 (+5次元)
- 役推定確率 yaku_prob (+21次元)
- 聴牌確率 tenpai_prob (+1次元)
- 4枚ハードマスク、赤牌所持ヘッド、global sum ソフト制約

多くの変更を一度に入れたため原因特定が困難。**1変数ずつ検証する。**

---

## 実験一覧

| 実験 | 仮説 | 変更点 | モデル名 | 状態 |
|------|------|--------|---------|------|
| A    | epochs=60 が上限に達しており収束不足 | epochs: 60→100 | v7 | 完了 |
| B    | yaku_prob/tenpai_prob が2ステージノイズ | input_dim: 371→349（末尾22次元除外） | v8 | 完了 |
| C    | d_model=128 が371次元入力に対して容量不足 | d_model: 128→256 | v9 | 実施中 |
| D    | v5の219次元特徴量自体がより優れている（v5もep60で未収束の可能性） | v5アーキテクチャ・特徴量のままepochs: 60→100 | v10 | C結果次第 |

実験順序: A → B → C → D（Cが大幅改善なら D は省略も可）

---

## 実験A: エポック数増加 (v7)

### 変更内容

```
MODEL_DIR : .../v6 → .../v7
epochs    : 60 → 100
追加      : per-epoch train_log.json（収束曲線保存）
```

アーキテクチャ・特徴量・損失関数はすべて v6 と同一。

### 判定基準

- `test_acc > 0.7891` → エポック不足が原因（少なくとも一部）
- early stopping が epoch 60 以前に発動 → v6 もエポック数は十分だったと確認できる
- train_log.json の収束カーブで次の実験のヒントを得る

### 結果 (2026-06-06)

- **test_acc: 0.7988**（v6比 +0.97pp → エポック不足が一部原因と確認）
- early stop: **発動せず**（epoch 100 まで継続、best = epoch 100）
- 収束カーブ: epoch 60時点で 0.7889、以降も微増が続くが改善速度は急低下（ep70以降 +0.001以下/epoch）
- v5 (0.8025) にはまだ届かず。v5も ep60 で未収束の可能性があるため単純比較に注意。

---

## 実験B: 2ステージ特徴量 ablation (v8)

### 変更内容

```
input_dim : 371 → 349
MODEL_DIR : .../v8
```

入力末尾の `yaku_prob(21) + tenpai_prob(1)` の22次元をスライスで除外。
データ側・特徴量生成スクリプトの変更は不要（features 配列の末尾22要素を無視するだけ）。

### 判定基準

- `test_acc > 0.7891` → yaku_prob/tenpai_prob がノイズだった
- `test_acc ≈ 0.7891` → 特徴量の問題ではない

### 結果 (2026-06-06)

- **test_acc: 0.7983**（v7比 -0.05pp、誤差の範囲内）
- early stop: **発動せず**（epoch 100 まで継続、best = epoch 99）
- **判定: 否定的**。yaku_prob/tenpai_prob の除去は精度に影響せず、ノイズ仮説は支持されなかった。

---

## 実験C: モデル容量増加 (v9)

### 変更内容

```
d_model   : 128 → 256
MODEL_DIR : .../v9
```

パラメータ数が約4倍になるため学習時間は増加する。他はすべて v6 と同一（371次元入力）。

### 判定基準

- `test_acc > 0.8025 (v5)` → 容量不足が主因
- `test_acc ≈ 0.7891` → アーキテクチャより特徴量設計の問題

---

## 実験D: v5特徴量・アーキテクチャでepochs増加 (v10)

### 変更内容

```
MODEL_DIR : .../v10
epochs    : 60 → 100
特徴量    : v5と同一（219次元）
d_model   : 128（v5と同一）
```

v5 の実装をそのまま ep100 で走らせる。v5 も ep60 で未収束だった場合、
「371次元化そのものが悪い」という仮説の検証になる。

### 実施条件

C（v9）の結果次第:
- C が大幅改善（test_acc > 0.80）→ D は省略可
- C が改善不十分 → D を実施し、219次元の真のポテンシャルを確認する

### 判定基準

- `v10 >> v7@ep100 (0.7988)` → 371次元の追加特徴量が有害（特徴量選択を見直す必要）
- `v10 ≈ v7@ep100` → 特徴量の差ではなく容量・アーキテクチャの問題
