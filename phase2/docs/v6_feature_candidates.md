# hand_inference v6 特徴量候補

v5 (Transformer, test_acc=0.8025) からの改善に向けた特徴量・アーキテクチャ候補のメモ。

---

## 0. 確率分布の整合性制約（根本的な問題）

### 現状のモデルが抱える構造的限界

現在のモデルは34牌それぞれの**周辺確率（marginal probability）**を独立に予測している。

```
出力: P(count_0), P(count_1), ..., P(count_33)  ← 34個の独立した分布
```

これは手牌全体の**同時分布（joint distribution）**ではない。そのため以下の2つの制約が保証されない。

| 制約 | 内容 | 対象 |
|---|---|---|
| **per-tile 制約** | `count[i] ≤ 4 - visible[i]`（→セクション1） | 各牌の周辺分布 |
| **global sum 制約** | `Σ_i count[i] = 13 - 3×n_melds` | joint distributionの性質 |

### なぜ重要か

もし周辺分布が真に正しく校正されているなら、以下が成立するはずである：

```
E_model[count_i] ≈ E_true[count_i]
⟹ Σ_i E_model[count_i] ≈ 13 - 3×n_melds
```

つまり **global sum 制約を満たせていないこと自体が、モデルの校正が不完全である証拠**である。「各牌の確率が正しい」と「合計が正しい」は本来セットで成立すべきものであり、片方だけ成立していても確率計算として完結しているとは言えない。

### 対応方針

**ハードマスク（per-tile）とソフト損失（global sum）の併用が現実的。**

```python
# global sum 制約をソフト損失として追加
expected_counts = (logits.softmax(-1) * torch.arange(5, device=logits.device)).sum(-1)  # [B, 34]
expected_total  = expected_counts.sum(-1)                                                 # [B]
target_total    = (13 - 3 * n_melds).float()                                             # [B]
loss += λ * F.mse_loss(expected_total, target_total)
```

global sum をハードに満たす方法（joint distributionの直接モデリング）は組み合わせ爆発により非現実的。ソフト制約で「整合性に向けた圧力」をかけるのが現実的な落とし所。

## 1. 保存則ベース（4枚制約）

### 背景
各牌は全部で4枚しか存在しない。自分の手牌と `visible_counts` から「残り何枚が未知領域にあるか」を確定できる。これは終盤ほど強い制約になる。

### 特徴量案
- `hidden_remaining[i] = 4 - visible_count[i] - self_hand_count[i]`（34次元）
  - 対象プレーヤーが保有しうる最大枚数の上限
  - `hidden_remaining[i] = 0` なら確実に持っていない

### アーキテクチャ案（ハードマスク）
特徴量として入れるより、モデル出力に**物理的に不可能なクラスを強制ゼロ**にするハードマスクとして実装する方が確実。

```python
# hidden_remaining[i] = k のとき count > k は -inf マスク
remaining = (4 - visible_counts - self_hand_counts).long()  # [B, 34]
mask = torch.arange(5) > remaining.unsqueeze(-1)            # [B, 34, 5]
logits = logits.masked_fill(mask, float('-inf'))
```

**終盤ほど効果大。学習で覚えさせるより保証として実装すべき。**

## 2. 見送りイベント（コールスルー信号）

### 背景
「他家が〇を捨てた際に対象プレーヤーがコールしなかった」という事実は、その牌を持っていない弱い証拠になる。ただし2つの制約がある：

1. **「選択肢がなかっただけ」問題**：推測者視点からは、対象プレーヤーがコール可能な手牌だったかどうかは分からない。1回のスルーは証拠として弱い。
2. **チーは上家限定**：ポンは誰の捨て牌でも可能だが、チーは上家（左隣）の捨て牌のみ有効。性質が異なるため分けて扱う必要がある。

### 確率的薄まりモデル
スルー回数の加算ではなく、**1回のスルーごとに事後確率が係数倍で下がる**乗算的な更新として捉える。

```
P(〇を2枚持っている | n回スルー) ∝ P(prior) × α^n
α: スルー巡目によって変化（序盤ほど1に近い＝弱い更新、終盤ほど小さい＝強い更新）
```

### 特徴量案
- `pass_pon_signal[i]`（34次元）：ポンスルーの加重和
  ```
  pass_pon_signal[i] = Σ (turn / max_turn)  ← 各スルー巡目の正規化値の和
  ```
- `pass_chi_signal[j]`：チースルーは牌単体ではなく「形（3牌の組み合わせ）」単位のため、設計が複雑。別途検討。

### 注意
- 推論時に観察可能な情報のみ使用可能（実際の手牌状態は使えない）
- 訓練データ生成時には真の手牌が分かるため「本当にコール可能だったか」を区別できるが、推論時には使えないため特徴量には含めない

## 3. 役推定パイプライン（2ステージ構成）

### 背景
手牌の種類（役）を先に推定できれば、所持牌の候補を大幅に絞れる。例：
- タンヤオ確定 → 1/9/字牌の所持確率をほぼゼロに
- 混一色確定 → 2色以上にまたがる手牌はほぼあり得ない
- 役牌狙い確定 → 字牌の枚数予測が上がる

### 設計方針：2ステージ独立学習
マルチタスク学習（共有エンコーダ）ではなく、**役予測モデルを先に単独で学習させ、その出力を手牌推定の特徴量として使う**。

```
[Stage 1] 捨て牌・鳴きパターン → 役推定モデル → P(タンヤオ), P(混一色), P(役牌), ...
                                                          ↓ (固定済みの推論結果)
[Stage 2] 219次元 + 役確率ベクトル → 手牌推定モデル → 枚数予測
```

理由：
- 役予測の方が学習難易度が低く（観察可能な情報から直接ラベルが取れる）、独立して改善できる
- ステージ単位でデバッグ・評価が可能
- behavior_clone の学習済みモデルとの組み合わせも検討余地あり

### 候補役クラス（例）
タンヤオ / 混一色 / 清一色 / 役牌（白・発・中・場風・自風）/ 平和 / チャンタ / リーチ（既存特徴量あり）

## 4. 赤牌対応

### 背景
取得牌譜のルールには各5（5m・5p・5s）に赤牌が1枚ずつ含まれる。赤牌は通常の5と区別して扱うべき理由が2つある。

### 現状調査結果（2026-05-30）

`extract_features.js` の `PAI_INDEX` で赤牌が通常5と**完全に統合**されており、パイプライン全体で赤牌の区別が存在しない。

```javascript
PAI_INDEX['m0'] = PAI_INDEX['m5'];  // 赤5m → 5mと同一インデックス
PAI_INDEX['p0'] = PAI_INDEX['p5'];
PAI_INDEX['s0'] = PAI_INDEX['s5'];
```

| 箇所 | 状況 |
|---|---|
| `discard_features(44)` | 赤5と通常5を合算カウント |
| `encode_hand()` ラベル | 赤5を通常5として枚数加算 |
| `visible_counts_vec()` | 赤5を通常5として合算 |
| `states.ndjson` 生データ | `m0`/`p0`/`s0` 文字列は**保持されている** ← 復元可能 |

`states.ndjson` の再生成は不要。`extract_features.js` の変更のみで対応できる。

---

### 4-1. 赤牌捨て＝強い不所持シグナル（特徴量追加）

**立直なしで赤5を切った場合、同種の5を1枚も持っていない可能性が非常に高い。**

通常の判断：
- 赤牌はドラ扱いで高得点につながる → 持っていれば可能なかぎり手元に残す
- 立直なし＋赤切り = 手組みの都合上5が不要 = 5自体を保有していない可能性大

```
red_discard_signal[suit] ∈ {0, 1}  ← 3次元（5m/5p/5s）
```

条件：`立直フラグOFF かつ 赤5を捨て牌に持つ`

セクション2の見送り信号と同様に確率的薄まりとして捉えられるが、赤切りは**1回で十分に強いシグナル**であるため binary 特徴量で表現する。

実装イメージ（`extract_features.js` への追加）：
```javascript
function red_discard_signal(discards, riichi) {
    if (riichi) return [0, 0, 0];  // 立直中は情報として使えない
    return ['m0', 'p0', 's0'].map(r =>
        discards.some(p => p.replace(/[_*+=\-]/g, '') === r) ? 1 : 0
    );
}
```

### 4-2. 赤牌所持枚数の出力追加（アーキテクチャ変更）

#### 現状の問題
現在の出力は34牌種×5クラスで、5mの「通常版」と「赤版」を区別しない。
赤牌の有無は戦略上重要な情報（手の打点推定に直結）のため、別途予測すべき。

#### 出力拡張案

赤牌は各スーツに最大1枚しか存在しないため、binary（0/1）の追加予測として扱う。

```
現行出力: logits[B, 34, 5]   ← 34牌種 × 枚数クラス
拡張出力: logits[B, 34, 5]   ← 変更なし（5mは赤込みの合計枚数）
        + red_logits[B, 3, 2] ← 赤5m/5p/5s の有無（binary）
```

あるいは37牌種に拡張して統一的に扱う方法もあるが、赤牌は最大1枚（クラス2以上は常にマスク）のため、binary 出力の方がシンプル。

#### 整合性制約

赤牌予測と通常牌予測は独立してはならない：

```
P(赤5pを持つ) ≤ P(5pを1枚以上持つ)
```

これもソフト制約として損失に追加できる。

#### データ要件（調査済み）
- `states.ndjson`：`discards_l` に `"p0"` 等の赤牌文字列が**保持されている** → 追加パースは不要
- `encode_hand()` の変更でラベルに赤牌フラグを追加できる
- `extract_features.js` のみ変更で対応可能（牌譜パース層の変更は不要）

実装イメージ（ラベル拡張）：
```javascript
function encode_hand_with_red(hand_str) {
    const vec = new Array(N_PAI).fill(0);
    const red = [0, 0, 0];  // [red_5m, red_5p, red_5s]
    // ... 通常カウント ...
    // 赤牌を別途カウント
    for (const c of base) {
        if (c === '0') red[['m','p','s'].indexOf(s)]++;
    }
    return { counts: vec, red };  // ラベルを拡張
}
```

## 5. シャンテン数・聴牌確率の扱い

### 2つの概念の性質

| | 役推定 | シャンテン数/聴牌確率 |
|---|---|---|
| ラベル取得 | 局終了時の役から確定的に取れる | 実際の手牌からアルゴリズムで**計算可能** |
| 観察信号との関係 | 捨て牌パターンから推測 | 捨て枚数・副露数・リーチフラグから推測 |
| 既存特徴量との重複 | 少ない | **多い**（捨て枚数・副露数・リーチフラグが既に入っている） |

### 役推定との根本的な違い

役推定を2ステージに分ける理由は「**役は局終了時の静的なラベル**で観察信号と独立した軸**」だから。

シャンテン数は**手牌内容から決定論的に計算できる**概念であり、「手牌推定の結果から計算できるもの」を「手牌推定の入力にする」ことになりかねず、**循環が起きやすい**。

```
× 観察可能情報 → 聴牌確率推定モデル → 手牌推定モデル（循環の危険）
```

また聴牌確率の推定に必要な信号（捨て枚数・副露数・リーチ）は既存特徴量に大部分含まれているため、独立ステージ化の恩恵が役推定より小さい。

### 推奨：出力側の整合性制約として使う

シャンテン数は入力特徴量ではなく、**予測手牌が現実の聴牌パターンと整合しているかを確認する損失**として使う方が設計として自然。

```python
# リーチ済みプレーヤー → 聴牌確定 → 予測手牌のシャンテン期待値が高ければペナルティ
expected_shanten = compute_expected_shanten(logits.softmax(-1))  # 手牌分布からシャンテン期待値
loss += λ * F.mse_loss(expected_shanten[riichi_mask], torch.zeros(...))
```

これにより「リーチしているのに聴牌形にならない手牌を予測する」ような矛盾を直接ペナルティとして学習できる。

### 実装優先度

| アプローチ | 評価 | 理由 |
|---|---|---|
| 別モデルで聴牌確率を学習 → 特徴量に追加 | △ | 既存特徴量との重複が大きく効果が薄い |
| 補助タスクとして聴牌分類を追加（マルチタスク） | ○ | 共有エンコーダが聴牌パターンを学習する圧力になる |
| **出力制約（整合性損失）として使う** | ◎ | 「リーチ=聴牌確定」等のハード知識を整合性損失として直接使える |

**実装順序の推奨**：global sum制約・4枚ハードマスクを先に実装してベースラインを改善してから、残余の誤差パターンを確認した上で聴牌整合性損失を追加する。
